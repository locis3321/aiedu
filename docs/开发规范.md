# 通用 AI Coding 开发工作指南

> 本文件面向 AI Coding Agent 与项目开发者，定义通用的代码修改原则、任务分级、过程记录、确认门和验收要求。
>
> 目标：让开发过程可理解、可追溯、可验证，避免以技术兜底掩盖业务事实错误。

---

## 0. 适用范围与指令优先级

本文件适用于当前仓库及其子目录。若子目录存在更具体的 `AGENTS.md`，处理该目录内文件时应同时遵循，并以更具体的规则为准。

发生冲突时按以下顺序处理：

1. 用户当前明确指令与已确认决定；
2. 目标文件所在目录最近的 `AGENTS.md`；
3. 仓库根目录 `AGENTS.md`；
4. 项目权威文档、接口契约、数据库结构和测试；
5. `docs/memory/` 中仍然有效的历史决策；
6. 现有实现风格与相邻代码。

若历史决定与当前代码冲突，不得静默选择一方：先查明是代码偏离、文档过期还是需求已经变化，并记录结论。

除非项目文档另有规定，用户最新明确决定可以取代旧决定，但必须保留旧记录并说明替代关系。

## 1. 每次任务开始前

开始修改前必须：

1. 阅读当前作用域内的全部 `AGENTS.md`。
2. 找到并阅读项目权威入口，例如 `README.md`、`CONTRIBUTING.md`、架构说明、接口文档和数据库文档、docs目录下的文档。
3. 检查工作区状态，识别用户或其他开发者已有的未提交修改。
4. 阅读目标文件、相邻实现、调用方、测试和相关配置，不孤立修改单个文件。
5. 确认项目实际使用的构建、测试、格式化和检查命令。
6. 若任务需要 memory 流程，先查阅历史任务中的相关决策，再拆解任务。
7. 评估是否涉及数据库写入、删除、生产环境、部署、外部消息、凭据或其他需要单独授权的动作。

不得凭经验假定项目使用某种框架、目录、分层、包管理器或测试工具。以当前仓库事实为准。

## 2. 业务一致性八项原则（强制）

这些原则是代码修改的硬约束。

1. **以主路径清晰为荣，以过度抽象为耻**  
   业务特例放在明确的业务路径中，不包装成无实际使用方的通用能力、隐式开关或魔法方法。

2. **以事实必填为荣，以自动乱选为耻**  
   必须存在的业务事实缺失时，应显式失败或阻断，不得随便取第一条、替换为其他值或伪造正常状态。

3. **以边界明确为荣，以配置运行混用为耻**  
   分清配置数据、主数据、业务数据和运行时状态，不用配置逻辑掩盖运行时错误，也不制造多个可写的事实来源。

4. **以窄域兜底为荣，以宽泛兜底为耻**  
   兜底必须有明确场景、输入条件和影响范围，不得使用大范围默认值、空对象或吞异常让错误看起来消失。

5. **以显式失败为荣，以延后暴雷为耻**  
   参数缺失、状态错误、关系不存在等问题应在最早可判断的位置暴露，不让错误数据继续流入下游。

6. **以关系一致为荣，以表面成功为耻**  
   创建、更新、绑定和删除必须保证业务归属、上下游 ID、状态机和关联关系一致，不能只追求接口返回成功。

7. **以局部特例为荣，以隐式副作用为耻**  
   特例处理应靠近触发它的业务分支，并写清条件；不得通过全局拦截器、公共转换器或默认查询制造隐藏副作用。

8. **以审慎变更为荣，以自作聪明为耻**  
   未确认业务含义前，不新增自动修复、批量补齐、历史脏数据兼容或静默降级。确需兼容时，必须说明范围、原因和失败策略。

### 2.1 修改前自检六问

每个代码修改子任务动手前必须回答：

1. 这个值是业务事实，还是可以配置的策略？
2. 缺失时应该失败，还是业务明确允许默认？
3. 兜底是否只覆盖一个明确场景？
4. 是否把业务特例伪装成了通用能力？
5. 是否可能产生“看起来成功但关系不一致”的数据？
6. 错误是在源头暴露，还是被延后到更难排查的位置？

任何一项答不清，暂停受影响的实现并向用户澄清。不要用猜测补齐业务语义。

## 3. 任务分级

| 级别 | 典型范围 | 默认处理方式 |
| ---------- | -------------------------- | -------------------------- |
| L1：局部小修改 | 文档、注释、小范围修复、明确的单点调整 | 直接修改，执行针对性验证，不强制创建任务包 |
| L2：模块功能 | 单一后端模块、前端模块或独立工具内的功能开发 | 先创建 memory 任务包并展示确认 |
| L3：跨边界联调 | 跨前后端、服务、存储、消息或外部系统 | 创建任务包，明确契约和依赖，安排集成或 E2E 验证 |
| L4：架构或数据模型 | 表结构、公共合同、依赖方向、构建系统、权限模型、迁移 | 先形成计划并获得确认；高风险动作另行授权 |

按影响、风险和不确定性分级，不仅看修改行数。短小的权限或数据库修改也可能属于 L4。

用户明确要求采用更轻或更重的流程时，按用户要求执行，但不得绕过必要的安全授权和验收证据。

### 3.1 功能分支与合并门禁（强制）

凡是修改程序行为的功能开发、缺陷修复、重构、接口调整、数据模型变更，必须在独立 Git 工作分支完成。纯文档、纯注释或不改变程序行为的维护任务可以豁免，除非用户另有要求。

#### 分支命名

优先遵循仓库已有规范；没有规范时使用：

```text
feature/<需求ID>-<简短英文描述>   # 新功能
fix/<需求ID>-<简短英文描述>       # 缺陷修复
refactor/<需求ID>-<简短英文描述>  # 重构
```

要求：

- 使用小写字母、数字和短横线；
- 分支名必须能关联整个需求或 memory 任务包；有正式 Issue、工单或需求编号时优先使用该编号，否则使用任务包目录中的时间标识，例如 `feature/2609-1614-30-user-profile`；
- 分支粒度是“需求/任务包”，不是单个子任务：一个 `docs/memory/tasks-*` 目录原则上对应一个工作分支；
- 同一任务包内的 `T1`、`T2`、`T3` 等子任务必须共用该工作分支，默认不得为每个子任务重复创建分支；
- 一个工作分支只承载一个需求任务包；新出现且可独立验收、独立发布的需求应另建任务包和分支；
- 不得直接在 `main`、`master` 或仓库定义的默认保护分支上开发。

#### 开始任务前

1. 确认当前目录是 Git 仓库，识别仓库实际默认分支，不得主观假定一定是 `main` 或 `master`。
2. 检查 `git status`。存在未提交修改时，先判断是否属于当前任务；不属于当前任务或归属不明时，停止并请求用户处理，不得自动 stash、覆盖或丢弃。
3. 确认当前不是 detached HEAD，也不是其他任务尚未完成的工作分支。
4. 按项目策略同步本地基准分支。禁止用 `reset --hard`、强制 checkout 等方式同步。
5. 从确认后的基准分支为整个需求任务包创建一次工作分支，再开始第一个子任务。
6. 在 `需求总览.md` 中记录基准分支、基准提交、需求工作分支和分支粒度。

后续子任务开始时，确认当前仍位于该需求工作分支并检查工作区状态，然后直接继续；不得嵌套创建 `feature/T1-*`、`feature/T2-*` 等子任务分支。若当前已经位于与本需求匹配的工作分支，确认来源和状态后继续使用，不再重复创建分支。

#### 开发与提交

- 所有代码、测试和任务文档修改均在工作分支完成。
- 每个子任务完成后执行与其改动匹配的静态检查、单元测试、模块测试或局部集成验证，不要求重复执行整套 E2E。
- 可以按子任务创建范围清晰的本地提交，并在提交信息或任务记录中关联 `T1`、`T2` 等编号；提交边界不改变分支边界。
- 本规则授权 Agent 为当前任务创建必要的本地提交；提交必须范围清晰，不混入无关修改。
- 提交信息优先遵循仓库规范；没有规范时使用 `feat:`、`fix:`、`refactor:`、`test:`、`docs:` 等清晰前缀。
- `git push`、创建或合并远程 PR/MR 仍需单独授权。

#### 子分支例外

只有任务计划明确需要多人/多 Agent 并行、实验性方案隔离或高风险改动隔离时，才可从需求工作分支创建临时子分支。临时子分支必须满足：

- 在 `需求总览.md` 或对应子任务文件中预先记录用途、负责人和回收路径；
- 只执行与该子任务匹配的定向验证，不要求在每个临时子分支重复完整 E2E；
- 完成后只合入需求工作分支，不得直接合入默认分支；
- 所有临时子分支汇总后，仍由需求工作分支统一执行完整 E2E 和最终合并。

#### E2E 合并门禁

需求工作分支合并回默认分支前，必须满足：

1. 任务包内所有必需子任务均已完成定向验证，依赖关系已经满足，任务状态和实际实现一致。
2. 已按仓库策略吸收默认分支的最新变化；默认优先将默认分支合入工作分支，未经允许不使用会改写历史的 rebase。
3. 编译、类型检查、单元测试和集成测试中适用的项目均已通过。
4. 汇总全部子任务后，在需求工作分支统一执行一次完整 E2E，包括关键正向流程和适用的异常/权限路径；只有受修复或默认分支变化影响时才重跑，不为每个子任务机械重复。
5. E2E 的环境、命令、版本/提交、结果和证据已写入任务记录。
6. 没有未解决的阻塞缺陷、未确认数据库操作或未获授权的高风险动作。

任一条件不满足：禁止合并，任务保持“进行中”“验收”或“阻塞”。不得通过跳过测试、修改测试数据、删除失败用例或使用假数据绕过门禁。

#### 合并回默认分支

1. E2E 通过后再次确认默认分支没有发生会影响结果的新变化；若发生变化，先重新集成并重跑受影响验证。
2. 切换到默认分支，确认工作区干净。
3. 按仓库既有合并策略执行本地合并；没有明确策略时，使用保留分支边界的非快进合并。
4. 推荐先形成未提交的合并结果并执行至少一轮合并后冒烟/关键链路验证；验证通过后再创建合并提交。
5. 合并后验证失败时，中止未完成的合并并返回工作分支修复，不得在默认分支上直接补丁式开发。
6. 在 memory 中记录 E2E 证据、合并结果和合并提交 ID，再将整个需求任务包标记为“完成”。

默认不自动删除工作分支。推送默认分支、删除本地/远程分支或远程合并仍需用户或项目流程授权。

## 4. Memory 任务记录

### 4.1 目录选择

优先使用项目已经存在并有明确约定的过程记录目录。没有约定时按以下顺序选择：

1. `docs/memory/`

不得同时创建多套 `.memory/`、`memory/` 或分散在各子项目中的记录目录。建议遵循`evidence-driven-task-delivery` 技能。

任务目录命名：

```text
tasks-YYMM-DDHH-MM
```

示例：`tasks-2609-1614-30` 表示 2026-09-16 14:30 创建。

Memory 中不得写入真实密码、Token、Cookie、私钥、内网敏感地址或可直接用于访问系统的完整凭据。

### 4.2 历史决策检索

创建新任务前，应扫描所有历史任务中的 `## 决策记录`，然后精读与当前模块、业务规则、接口契约或数据模型相关的任务文件。

重点识别：

- 可直接复用的决定；
- 与当前需求冲突的旧决定；
- 会影响接口、数据或执行顺序的约束；
- 已经失败或被用户否决的方案。

不要把所有历史内容无差别加载进上下文。先建立决策索引，再读取相关原文。

### 4.3 `需求总览.md`

L2～L4 任务必须创建根节点文件：

```markdown
# 需求：{需求名称}

## 背景

## 现状盘点
### 已有
### 缺口
### 未知与约束

## 需求定位（项目 / 服务 / 模块 / 方法 / 实现 / 逻辑）

## 任务树（与项目结构对齐）
- 需求总览
  - T1：{子任务}
  - T2：{子任务}

## 子任务列表
| 任务 ID | 文件 | 状态 | 依赖 |
|---|---|---|---|
| T1 | T1-{名称}.md | 创建 | - |
| T2 | T2-{名称}.md | 创建 | T1 |

## 验收方式

## 当前状态
展示确认（等待用户确认任务分解后进入执行）

## 备注
```

每个子任务必须自洽，至少包含：

```markdown

## 状态记录表
| 阶段 | 时间 | 说明 |
```

## 5. 任务拆解规则

1. 先盘点现状，再设计改动；不根据文件名或用户描述猜测现有能力。
2. 任务树尽量与真实项目、服务和模块边界对齐。
3. 按“可独立验收的能力”拆分，不机械按 Controller、Service、Repository 或每个文件拆分。
4. 每个任务只承担一个连贯结果，并明确输入、输出、影响、依赖和验收。
5. 合同、数据模型和权限模型未稳定前，不并行实现依赖它们的任务。
6. 只有在文件、合同、状态和环境不冲突时才并行。
7. 高风险未知应优先拆成验证任务、技术实验、合同测试或迁移演练。
8. 跨边界需求应包含最终集成或 E2E 任务，验证完整用户旅程。
9. 数据库修改、生产操作、删除和外部变更必须在任务中明确标记为待授权。
10. 不为简单任务制造形式化文档；不为复杂任务隐藏必要步骤。

验收项应采用：

```text
前置状态 + 操作 + 可观察结果 + 证据来源
```

避免使用“功能正常”“测试通过”等不可复核描述。

## 6. 展示确认门

任务文件创建后、代码修改前，必须向用户展示：

- 任务目录的完整文件列表；
- 每个任务的 ID、名称、核心需求或输出；
- 依赖关系以及可并行、必须串行的任务；
- 参考的历史决策和待决定事项；
- 总体验收方法；
- 需要单独授权的高风险动作。

等待用户确认后再进入执行。用户要求调整时，先更新任务文件，再重新展示变更后的任务结构。

用户已明确授权“按合理方案自主完成”或明确跳过计划确认时，可以不等待二次确认，但仍须保留任务记录，并且不得把该授权扩展到数据库写入、删除、生产部署、外部消息或其他高风险操作。

## 7. 执行、状态与决策记录

任务主状态：

```text
创建 → 展示确认 → 进行中 → 验收 → 完成
                      ↘ 阻塞
```

每个子任务执行顺序：

1. 读取任务文件，确认依赖满足且当前状态正确。
2. 写入真实启动时间，状态变更为“进行中”。
3. 回答修改前六问；答不清则进入阻塞或请求澄清。
4. 在已授权范围内实施修改。
5. 及时更新实际改动文件、偏差、失败和发现。
6. 执行任务验收并记录完整命令与结果。
7. 验收通过后填写结束时间、实际时长和状态。
8. 同步更新 `需求总览.md`。

### 7.1 决策必须即时记录

遇到以下事项时立即写入当前任务的决策表：

- 方案或依赖选型；
- 架构和模块边界；
- 数据模型和状态机；
- 业务规则与失败策略；
- 接口契约和兼容方案；
- 需求或范围变化；
- 外部系统集成方式；
- 推翻或替代历史决定。

不得在任务结束时凭记忆批量补写，也不得删除旧决定。新决定取代旧决定时，应明确替代对象、原因和影响。

## 8. 修改红线与授权边界

未经明确授权，不得：

- 执行 DDL、DML、数据修复、批量更新或删除；
- 删除、覆盖或移动范围不明确的文件；
- 修改生产环境、部署服务、发布版本或变更外部系统；
- 发送邮件、消息、工单或其他对外内容；
- 执行 `git commit`、`git push`、创建 PR 或改写 Git 历史；
- 修改与当前需求无关的配置、依赖或代码；
- 引入自动修复、批量补偿或宽泛兼容机制；
- 覆盖用户或其他开发者已有的未提交修改。

可以在任务范围内准备 SQL、迁移脚本或部署方案，但执行前必须单独确认。

发现附带问题时：若它是完成当前任务必需、风险低且处于授权范围，可以修复并记录；否则登记为后续任务，不静默扩大范围。

## 9. 代码与工程约定

- 修改前阅读目标文件和相邻实现，保持当前项目风格。
- 优先复用现有合同、公共组件和工具，避免重复造轮子。
- 不新增无意义的 README、示例、脚本、兼容层或配置文件。
- 不因为个人偏好进行无关重构、格式化或依赖升级。
- 代码注释解释“为什么”和业务约束，不重复代码表面行为。
- 异常必须有明确语义，不吞异常后返回成功。
- 日志不得包含密码、令牌、Cookie、个人信息或完整敏感载荷。
- 重构应保持外部行为合同，并用回归测试或等价证据证明。
- 发现工作区已有改动时，先理解其目的；无法安全共存时请求用户决定。

### 9.1 命令与工具

- 优先使用项目已有脚本和工具，不重新发明构建流程。
- 根据当前操作系统和 Shell 生成命令，不假定 Bash、PowerShell 或 CMD 语法互通。
- 长时间命令应使用可观察的后台机制，并保留日志与退出状态。
- 运行格式化工具前确认作用范围，避免产生大面积无关变更。
- 搜索文件和内容时优先使用高效、可限定范围的搜索工具。

## 10. 验证与完成标准

按风险选择验证层级：

| 改动类型     | 最低验证证据              |
| -------- | ------------------- |
| 文档/配置    | 格式或解析检查，必要时验证加载结果   |
| 内部逻辑     | 聚焦单元测试及相关回归         |
| 编译/类型/合同 | 编译、类型检查或合同测试        |
| API      | 真实请求、响应、错误路径与权限检查   |
| 数据持久化    | 服务结果与数据库状态或事务证据     |
| 异步任务     | 触发记录、日志/队列和最终状态关联   |
| UI       | 浏览器真实操作、页面结果和关键网络请求 |
| 权限/租户    | 允许路径、拒绝路径和隔离负例      |
| 迁移/兼容    | 迁移前后样本、恢复或回滚路径      |
| 跨模块功能    | 完整 E2E 用户旅程和各边界证据   |

必须遵守：

- 编译成功不等于业务完成。
- HTTP 200 不等于 UI 或数据关系正确。
- Mock 通过不能替代用户要求的真实集成验证。
- 没有数据时展示真实空状态，不用假数据制造成功效果。
- 测试失败后保留失败证据；修复后记录复测，不覆盖首次失败。
- 环境无法验证时，明确区分“未验证”和“验证失败”。
- 质量数字必须来自项目要求、用户要求或测量基线，不虚构通用阈值。

只有在以下条件全部满足时才能标记完成：

1. 实际输出与任务文档一致；
2. 验收项均有可复核证据；
3. 必要的错误路径和回归已经覆盖；
4. 依赖任务完成；
5. 未执行的危险动作没有被描述成已完成；
6. 缺陷、限制、未验证项和残余风险已明确；
7. 总览、子任务和 E2E 记录状态一致。

## 11. 安全与凭据

- 真实凭据只能通过项目认可的环境变量、秘密管理系统或本地忽略配置注入。
- 不把密码、Token、私钥、Cookie、数据库连接串或敏感内网地址写入 `AGENTS.md`、memory、代码、测试样本和聊天回复。
- 即使凭据已经出现在仓库或用户材料中，也不得再次复读或传播。
- 发现疑似真实凭据时，提醒用户轮换，并在不泄露值的前提下指出位置与类型。
- 示例值必须明显无效，例如 `example.invalid`、`<TOKEN>`、`${DB_PASSWORD}`。
- 提交前检查暂存内容、生成文件和日志，避免秘密被意外纳入版本控制。
